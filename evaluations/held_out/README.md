# Held-Out Evaluation Fixture (T081, PRD §16.1)

`fixture.json` (generated by `generate_fixture.py`, seed 7) is a fully synthetic, repository-owned
dataset: 20 histories (300–600 messages each), 100 labeled queries split by history — 12
histories/60 queries for development, 8 histories/40 queries held out (32 answerable, 8
absent-answer).

Each history exercises topic switches, superseded ("conflicting") decisions, repeated
statements with distinct identity, tool-call records, and cross-session references (multiple
`source_id` values within one history). Each answerable query names the exact message and a
codepoint span within it that must appear in a correct retrieval's excerpt, plus the correct
current value and any superseded value a correct answer must not cite.

**The held-out split (`held-h*` histories, `split: "held_out"` queries) is reserved for release
validation only — never tune retrieval, prompts, or scoring logic against it** (PRD §16.1).
Regenerate `fixture.json` only when the generator itself changes; do not hand-edit it to fix a
failing run.

## Regenerating

```bash
python3 generate_fixture.py           # writes fixture.json
python3 verify_fixture.py             # self-check: counts, span resolution
```

## Running the evaluation (T082)

See `run_evaluation.py` in this directory. It requires a real configured model provider (PRD
§16.2: "Run real-provider quality evaluation three times with isolated memo namespaces") — with
no provider configured, it runs in `--fake-provider` mode instead, which proves the harness's
control flow and scoring logic deterministically (PRD §16.3's own guidance for using a fake
provider) but does **not** produce a meaningful SC-011 quality result.
